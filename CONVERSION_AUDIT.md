# Аудит корректности ino2ubi — 2 ноября 2026 г.

## Назначение

Это промежуточная инженерная сборка на основе загруженного пользователем `ino2ubi_UL_SUPPORTED_GITHUB_PAGES.zip` — последней сборки проекта с работавшими преобразованиями BLE и поддержкой `60000UL`.

**Цель:** не выдавать `.ubi`, заведомо теряющий семантику C++, и устранить воспроизводимые ошибки преобразования. Статический анализ не компилирует C++ и не может гарантировать корректную работу в FLProg.

## Матрица девяти направлений

| № | Риск | Что изменено | Текущее ограничение |
|---|---|---|---|
| 1 | Порядок выполнения и объявлений | Сохранена проверка `return` в общих `setup/loop`; добавлен контроль зависимых глобальных инициализаторов, которые генератор может переставить. | Порядок выполнения всех Arduino-конструкций в FLProg не доказан, нужен итоговый `.ino` из FLProg. |
| 2 | `String`, `char`, `bool`, числа | Исправлено ошибочное преобразование `bool` в Code Basic; добавлены строгие проверки и нормализация числового `char`, `bool`, `float`, `double` в Basic/Professional; сохранена поддержка `60000UL`. | Сложные C++ выражения в значениях `// par` не вычисляются; строки с особыми escape-последовательностями требуют проверки после экспорта. |
| 3 | Параметры пользовательских функций | Проверяется количество параметров; аргументы по умолчанию, variadic и указатели на функции блокируются, если перенос не доказан. | Полная поддержка всех C++ сигнатур, шаблонов, перегрузок не реализована. |
| 4 | BLE, Wi-Fi, ESP-NOW callback | Сохранена поддержка BLE callback; обнаруживается прямой доступ ESP-NOW/Wi-Fi callback к входам/выходам/параметрам FLProg. | Произвольные лямбды и сторонние callback не анализируются как C++ компилятором; передача данных между задачами требует ручной проверки. |
| 5 | Повторная инициализация | Диагностика прямой инициализации `BLEDevice::init` / `esp_now_init` в каждом проходе `loop()`. | Защищённые ветвления не блокируются автоматически; конфликты использования всех периферийных устройств аппаратно не проверяются. |
| 6 | Конфликты имён | Проверяются пересечения идентификаторов функций/переменных/макросов, зарезервированные имена `__ino2ubi_*`. | Коллизии, возникающие только при объединении разных пользовательских блоков в FLProg, требуют проверки итогового проекта. |
| 7 | `#define`, `#ifdef`, условная компиляция | Экспорт блокируется при директивах `#if/#ifdef/#ifndef/#else/#elif/#endif`, не сохраняемых генератором; также при функциональных и многострочных макросах. | Нет автоматического препроцессинга для всех платформ: пользователь должен адаптировать скетч под конкретный Core. |
| 8 | Экранирование XML | Сохранено экранирование XML в генераторах; добавлена проверка недопустимых XML 1.0 управляющих символов и диагностика строки. | SIXX-структура и парсинг XML не заменяют импорт в FLProg. |
| 9 | Сосуществование блоков | Code Basic помечается «один экземпляр» при BLE, ESP-NOW, Wi-Fi, Wire, SPI и Serial владельцах; сохранена защита от раннего `return`. | Code Professional и взаимодействие с другими блоками требуют интеграционного теста, включая общий Wi-Fi/BLE, GPIO, NVS и ISR. |

## Что сознательно НЕ сделано

- нет универсального автоматического переписывания классов, макросов, callback и чужого кода — такое изменение может нарушить функциональность;
- не утверждается полноценная компиляция Arduino-ESP32 или запуск в FLProg;
- нет универсальной автоматической дедупликации аппаратной инициализации между независимыми пользовательскими блоками;
- не гарантирована обработка произвольных C++ конструкций сложнее поддерживаемого подмножества.

## Запуск тестов (Node.js)

```text
node tests/conversion-regression.js
node tests/ble-regression.js
node tests/numeric-regression.js
```

При сборке проверены: 35 сценариев преобразования, 11 сценариев BLE и 30 допустимых/ошибочных числовых литералов, синтаксис JavaScript, корректность SIXX-ссылок и XML 1.0 в двух примерах Code Basic. Тест Code Professional в реальном браузере не удалось завершить в доступной среде — его экспорт и импорт требуется проверить отдельно.

## Рекомендуемая последовательность проверки в FLProg

1. Сначала выгрузить и скомпилировать простой блок с типами `bool`, `char`, `String`, `float`, `unsigned long` в Code Basic и Professional.
2. Повторно экспортировать и скомпилировать ранее работавший BLE Presence с двумя MAC-адресами.
3. Проверить отдельный тест с ESP-NOW callback и передачей состояния в `loop()` без прямого обращения к контактам из callback.
4. Добавить два экземпляра любого обычного блока и убедиться, что его функции не мешают соседним блокам.
5. Добавить блок с Wi-Fi/BLE ресурсами только в одном экземпляре; затем проверить, что другие функциональные блоки используют общий ресурс без повторной инициализации.
6. Для любых обнаруженных расхождений приложить исходный `.ino`, `.ubi` и итоговый `.ino` FLProg — только по этой тройке можно доказать, какая трансформация сломала исходную логику.
