### Разрешение нескольких экземпляров (Code Professional)

В настройках блока установлен флажок «Использовать блок несколько раз в одном проекте FLProg» (по умолчанию ВЫКЛЮЧЕН).
В экспортируемом `.ubi` это поле `isUseItOnce`: `False` при включённой галочке (разрешены повторные экземпляры) и `True` при выключенной (один экземпляр).
Выбор сохраняется в `.i2u.json` как `settings.allowMultipleInstances` и восстанавливается при открытии проекта; отсутствующее поле в старом проекте означает включённую галочку.
Диагностика запускается повторно при переключении режима и перед экспортом. Проверки изоляции состояния, например запрет глобальных `static` и массивов при нескольких экземплярах, применяются в многократном режиме. Прочие ограничения парсера и общих ресурсов остаются для обоих режимов.
Проверка в браузере не заменяет импорт в FLProg и фактическую компиляцию проекта с несколькими экземплярами.

Тест: `python tests/instance-mode-browser.py` (требуются Playwright и Chromium).

### RC4 local-variable UUID fix (FLProg 9.8.6)

When "Использовать блок несколько раз" is enabled, simple automatic scalar declarations in `setup()` and `loop()` (e.g. `uint32_t curTm = millis();`) now receive a native per-instance FLProg UUID suffix in both declarations and references. This avoids duplicate local declarations if FLProg concatenates code fragments into one function scope. With the checkbox off the original identifiers remain unchanged. Global UUID handling and En behavior are unchanged.

This is intentionally a conservative transformation: complex C++ local declarations (structured bindings, custom classes, pointer/reference declarations, compound declarator lists) are not yet automatically isolated; verify generated FLProg C++ for these cases. A browser/g++ regression is included in `tests/local-uuid-browser.py`.


## RC4 hardening: многократные экземпляры (16.11.2026)

- В Code Professional при включённой опции нескольких экземпляров простые глобальные `static`-скаляры и `static`-массивы примитивных типов получают стандартный тег UUID FLProg; исходный квалификатор `static` сохраняется.

## Эксперимент: список выбора в свойствах готового блока FLProg

Для числового параметра Code Professional можно указать варианты в комментарии объявления:

```cpp
uint8_t Mode = 1; // par: Mode | choices: 0=Выключено; 1=Автоматически; 2=Вручную
```

Пары разделяются `;`, слева — значение, справа — подпись у радиокнопки. Требуются минимум два варианта; значение по умолчанию должно совпадать с одним из них. Без `| choices:` сохраняется обычный редактор параметра. Значения проверяются на допустимый диапазон типа; повторяющиеся значения отвергаются. Варианты сериализуются как `UserCodeMultiBlockRadioButtonParametrSpecies` с коллекциями `choices` и `booleanChoices`, по образцу файла FLProg «04.Изменение числовых форматов (Code - Professional).ubi». **Реальное отображение в FLProg 9.8.6 ещё нужно проверить импортом тестового блока**: XML-проверка не заменяет открытие окна свойств.

Уточнение по официальным исходникам ESP32 Core 2.0.17: analogWrite(pin,value), analogWriteFrequency(freq), analogWriteResolution(bits), ledcChangeFrequency(channel,freq,bits) и SET_LOOP_TASK_STACK_SIZE поддерживаются. Ложные запреты удалены.


## Внешние Wi-Fi-блоки FLProg (инструкция v10)

Для проектов с ESP32 Core 2.0.17 (по умолчанию) и 3.3.11 подключение, настройку и переподключение Wi-Fi выполняют отдельные блоки схемы FLProg. Пользовательские блоки INO2UBI Code Professional (.ubi) не должны повторно вызывать `WiFi.begin()`, `WiFi.mode()` или создавать собственный сетевой стек без явно согласованной архитектуры. Стандартные заголовки ядра и внешние блоки схемы FLProg — разные понятия. Полные правила — в `INO2UBI_AI_GUIDE_v10.txt`, разделы 6А.3 и 6Б.

### Описание параметров в `.ino` (добавлено)

Для экспорта **Code Professional** можно указать русскую подпись и отдельное описание параметра:

```cpp
float bedLengthM = 4.0f; // par: Длина грядки, м | description: Используется для расчёта площади испарения и осадков.
```

Текст после `par:` до служебного разделителя становится названием параметра в FLProg. Текст после ` | description: ` записывается в XML-поле `description` параметра. Поддерживаются русские символы, пробелы и знаки препинания. Ранее поддерживавшиеся объявления без `description:` продолжают работать.

`choices:` совместим с описанием, порядок секций произвольный:

```cpp
uint8_t Mode = 1; // par: Режим работы | choices: 0=Выкл; 1=Авто | description: Режим управления поливом.
uint8_t Mode = 1; // par: Режим работы | description: Режим управления поливом. | choices: 0=Выкл; 1=Авто
```

Для пользовательских параметров по-прежнему рекомендуется использовать настоящие переменные, а не `#define`.


## Справка актуальной сборки (23.11.2026)

Встроенная справка в `index.html` и полный текст `INO2UBI_AI_GUIDE_v10.txt` согласованы с текущим парсером и генератором Code Professional.

- первая содержательная строка начального комментария `.ino`: `Название блока: EnglishName`;
- вход `// in`, выход `// out`, внутреннее состояние `// variable`;
- параметр: `float bedLengthM = 4.0f; // par: Длина грядки, м | description: Пояснение для свойств FLProg.`;
- радиокнопки: `uint8_t Mode = 1; // par: Режим | choices: 0=Выкл; 1=Авто | description: Выбор режима.`;
- `description:` и `choices:` применяются только к параметрам, могут следовать в любом порядке;
- обычный Code Professional и экспериментальный импорт RemoteXY — отдельные маршруты, без обещания одинаковых меток;
- ESP32 Core 2.0.17 по умолчанию, Core 3.3.11 — выбор для диагностики; реальные `.ubi` и C++ надо проверять в FLProg.

Справка документирует реализованную поддержку XML `description`; фактическое отображение в конкретной версии FLProg требует импортирования `.ubi`.
