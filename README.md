# ino2ubi v2.16 + Code Professional (CRASHFIX PREVIEW)

Браузерный конвертер `.ino → .ubi` для FLProg 8 / ESP32 Arduino Core 2.0.17. Исходная версия v2.16 сохранена в режиме **Code Basic**: по-прежнему показываются только ошибки (без предупреждений).

## Установка на GitHub Pages

- Распакуйте архив и загрузите **все файлы и папку `icons/` из него** в корень репозитория `ino2ubi` (удобнее через GitHub Desktop);
- включите в Settings → Pages: Deploy from a branch, main, `/(root)`;
- при обновлении убедитесь, что загрузился новый файл `professional.js` и `professional-template.xml`.

**Рекомендуется сначала сохранить резервную копию рабочей v2.16 или протестировать эту экспериментальную сборку в отдельной ветке/репозитории.**

## Использование

- вставьте или откройте скетч `.ino` и нажмите «Парсить код»;
- задайте роли переменных (вход, выход, параметр) двойным щелчком по строке;
- в разделе «Формат экспорта FLProg 8» выберите Code Basic либо Code Professional;
- нажмите «Сгенерировать .ubi» (Basic) или «Сгенерировать Code Professional .ubi»;
- для Professional распакуйте ZIP, импортируйте `.ubi` в FLProg и скопируйте папку `ArduinoLibrary/<имя>/` в `ideV8/portable/sketchbook/libraries/` и перезапустите FLProg.

### Когда создаётся `.hpp`

- обычные вспомогательные функции включаются прямо в `.ubi`, без генерации лишнего `.hpp`;
- отдельный `.hpp` добавляется только если его содержимое явно передано через поле библиотеки или загружено пользователем;
- если нужен собственный класс/драйвер, загрузите его `.hpp`/`.h` через поле загрузки, либо вставьте его код в текстовое поле; файл будет добавлен в ZIP;
- существующие внешние `#include "имя.hpp"` не подменяются пустыми библиотеками: если исходников нет, зависимость перечисляется в README.txt архива и её необходимо установить отдельно;
- если `.hpp` не требуется, архив содержит только `.ubi` и `README.txt`.

### Исправление падения FLProg 9.8.0

В отчёте FLProg был сбой `Message not understood: #isInput` при компиляции блока `Professional_Test`. Исправлено первичное размещение объектов контактов и параметров непосредственно в `codeTag` (как в реальных SHT3x/NTC файлах), ссылки библиотеки заменены `sixx.idref`, экземпляры типов сериализуются без повторного вложенного ссылки. Это устранение выявленного несоответствия формату; проверить компиляцию исправленного `.ubi` в установленной FLProg всё ещё необходимо.

## Ограничения preview

**Структурный тест MultiBlock — не проверка FLProg.** Генерация основана на реальном примере SHT3x (`UserCodeMultiBlockBlockLibraryElement`). Автоматические проверки включают XML-парсинг, целостность ссылок `sixx.id`/`sixx.idref`, упаковку ZIP и регрессионный экспорт Code Basic. **Импорт созданного Code Professional в установленный FLProg 8 и компиляция на ESP32 пока не подтверждены.** Нестандартные классы, сложные шаблоны, массивы и параметры выбора могут потребовать ручной доработки; в автоматическом режиме создаются обычные скалярные параметры.

При проверке в FLProg начните с `examples/SIMPLE_Professional_Test.ino`, импортируйте полученный блок, соедините `In`/`Out`, установите параметр `gain` и скомпилируйте. При ошибке пришлите журнал FLProg, чтобы проверить конкретную секцию.

## FIX3: только необходимые библиотеки

Функции скетча больше не вызывают автоматическое создание `.hpp`: они остаются в UBI. `.hpp` поставляется только при явном предоставлении содержимого библиотеки. Папка ArduinoLibrary совпадает с безопасным именем экспортируемого блока. Отсутствующие внешние зависимости не создаются автоматически.

## FIX8: единый редактор и автоматическое решение о .hpp

- для обычных скетчей создаётся только `.ubi` (вспомогательные функции остаются в секциях UBI);
- отдельного поля ручного ввода `.hpp` нет;
- подключения внешних заголовочных файлов сохраняются и перечисляются как зависимости в README архива;
- создать исходный код отсутствующей сторонней библиотеки из `#include` невозможно: фиктивные `.hpp` не создаются;
- если проекту требуется собственная отдельная библиотека, её исходники нужно предоставить как отдельный артефакт для будущего импорта; этот режим пока не реализован;
- Code Basic без изменений.

## FIX9: Code Professional — один файл .ubi

Code Professional экспортируется напрямую как `<имя_блока>.ubi`, без ZIP и README внутри архива.
В FIX9 исходный `.ino` обрабатывается общим парсером, и собственный `.hpp` автоматически не создаётся. Внешние `#include` сохраняются; конвертер не делает вывод, установлены ли эти библиотеки в FLProg. Code Basic и кнопка «Открыть файл / проект» сохранены.


## FIX10 — отображаемые имена параметров Professional

Для переменной `float Setpoint = 25; // par: Температура уставки` в Code Professional отображается «Температура уставки», а в C++ остаётся имя `Setpoint`. Аналогично `#define TIMEOUT 3000 // par: Время ожидания, мс`. Для обычного `// par` без подписи используется исходное имя. Псевдоним также можно изменить в таблице после парсинга. Code Basic и экспорт Professional в один `.ubi` сохранены.

## FIX11 — уникальные ID Code Professional

При каждом экспорте Code Professional заново назначаются логические идентификаторы
объектов FLProg (`SmallInteger` с именем `id`), включая ID блока из шаблона.
Внутренние ссылки `editorPositionStore/expandElements` синхронизируются.
Это предотвращает конфликт новых блоков с одинаковыми ID образца.
SIXX `sixx.id` / `sixx.idref` не меняются. Code Basic не изменён.
Импорт и компиляцию требуется подтвердить в FLProg 9.8.0.

## FIX12 — имена параметров Code Basic

В Code Basic исправлено отображаемое имя параметра `#define` с `// par: Описание`:
теперь берётся псевдоним из парсера, а не машинное имя макроса.
Параметры-переменные с `// par: Описание` уже поддерживались и не изменялись.
Генератор Basic использует собственные последовательные SIXX ID и новые UUID; проблема
копирования постоянных ID из шаблона Professional к нему не относится.
Code Professional остался без изменений по сравнению с FIX11.

## FIX14 — параметр String в Code Basic и Code Professional

При подстановке параметра `String foo = "text"; // par` FLProg может передать
в код строковый литерал `"text"`. Выражения `foo.c_str()` и сравнение
`foo != activeString` тогда могут не скомпилироваться. В FIX14 введена
**одна общая обработка** `string-params.js`, вызываемая обоими генераторами:

- после разбора кода находятся именно строковые параметры роли `// par`;
- в `setup()`, `loop()` и вспомогательных функциях используются локальные
  переменные типа `String`, создаваемые из параметра при каждом исполнении;
- комментарии, строковые литералы, обращения к полям, директивы препроцессора
  и одноимённые формальные аргументы функций не изменяются;
- выходные `.ubi` сохраняют прежний формат и таблицу параметров;
- скетчи без строковых `// par` не получают новой трансформации.

Пример итогового кода после подстановки параметра FLProg:

```cpp
{
  String __ino2ubi_string_nvsNamespace = "sntp_cfg";
  prefs.begin(__ino2ubi_string_nvsNamespace.c_str(), true);
}
```

**Проверка:** оба генератора прошли тест XML, проверки SIXX id/idref,
регрессионный пример с числовыми параметрами и тест преобразования SNTP.
Импорт и компиляция FIX14 в FLProg 9.8.0 ещё не проверены. Не изменяются
глобальные объявления, дополнительные внешние заголовки и RemoteXY.
Перед обновлением GitHub Pages сохраните рабочую v2.16 FIX13; новую версию
сначала проверьте на тестовых блоках в Code Basic и Code Professional.
