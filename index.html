1. Основная задача
Создавай полный, самостоятельный Arduino-скетч .ino строго под конкретное задание. Один и тот же исходный скетч должен, насколько позволяет его логика и поддерживаемые конструкции, подходить для обоих режимов ino2ubi — Code Basic и Code Professional.

Порядок работы: вставить .ino в редактор → нажать «Парсить код» → проверить распознанные входы, выходы, параметры и описание → выполнить проверку ESP32 → выбрать нужный формат → экспортировать .ubi → импортировать в FLProg 9.8.0 → проверить итоговый код и компиляцию.

Не подменяй задачу универсальным шаблоном и не обещай совместимость без проверки. Если пользователь просит доработать только инструкцию, не изменяй сам ino2ubi или MQTT-скетч без отдельного запроса.

Если запрошен режим «Открыть скетч» и автоматический разбор чужого .ino: не назначай GPIO самостоятельно, не считай Serial.print()/Serial.println() выходами блока; назначение входов и выходов подтверждай по логике исходника и правилам парсера. Не придумывай контакты и параметры, которых не было в исходном алгоритме.

2. Обязательное описание блока
Первые символы скетча — многострочный комментарий /* ... */, до #include и любых объявлений. ino2ubi использует этот комментарий для поля описания блока.

Название блока размещай в первой строке описания в формате «Название блока: SNTP Time Sync». Используй короткое понятное имя, желательно не длиннее 24 символов; описание не должно подменять название. Описание пиши на русском языке. Оно должно содержать:

название и назначение блока;
понятное описание алгоритма;
все входы, выходы и параметры: имя, C++-тип, смысл, единицы измерения, диапазоны;
значения при запуске, отключении, ошибках и повторном включении;
используемые GPIO, аппаратные ресурсы и библиотеки;
особенности ESP32 и установки блока в FLProg;
ограничения работы нескольких экземпляров, если есть.
Если какой-то раздел неприменим, отметь это кратко. Описание не должно противоречить реализации.

3. Объявления и метки ino2ubi
Объявляй входы, выходы и параметры как глобальные переменные поддерживаемого простого типа. Метку пиши на той же строке, что и объявление.

bool inEnable = false;           // in
uint32_t inInterval = 1000;      // in
bool outReady = false;           // out
int Timeout = 3000;              // par: Время ожидания, мс
float Setpoint = 25.0f;          // par: Температура уставки
uint32_t previousMs = 0;        // variable
            
Значение меток:

// in — вход из схемы FLProg; не переписывай его в setup() и loop();
// out — выход, которым управляет блок;
// par — редактируемый параметр блока; предпочитай форму // par: с обязательным описанием;
// par: Описание параметра — обязательная понятная русская подпись для настроек блока; её отображение нужно проверить отдельно в Code Basic и Code Professional;
// variable — внутреннее состояние или служебная переменная.
Важно: // par: ... — это отдельная подпись параметра. Не переименовывай ради неё C++-переменную, используемую в вычислениях. Оставлять подпись пустой запрещено; исходное C++-имя нельзя заменять подписью, иначе появятся ошибки подстановки.

ОБЯЗАТЕЛЬНОЕ ПРАВИЛО ДЛЯ ОПИСАНИЙ ПАРАМЕТРОВ
Каждое объявление // par: должно содержать конкретное, краткое, читаемое русское название, отражающее функцию настройки; не используй только идентификатор, общее слово «Параметр» или пустой комментарий.
Примеры:
String defNtpServer = "pool.ntp.org"; // par: Адрес NTP-сервера
String defTzString = "UTC0"; // par: Часовой пояс POSIX
String nvsNamespace = "sntp_cfg"; // par: Имя пространства памяти NVS
uint32_t updateInterval = 1000; // par: Интервал обновления, мс
bool autoStart = true; // par: Автоматический запуск

В первом комментарии к блоку отдельно объясняй для каждого параметра C++-имя, тип, назначение, значение по умолчанию, допустимый диапазон, единицы измерения и последствия изменения во время работы (где применимо). Не ожидай, что длинное описание из шапки само заполнит подпись параметра: именно // par: задаёт краткую подпись. После «Парсить код» проверь наличие подписи в таблице параметров ino2ubi, а после импорта — в окне параметров FLProg в каждом формате. Если подпись исчезла, это проблема обработки метки или экспорта и должна исправляться, а не маскироваться переименованием исходного C++-идентификатора. Названия и значения всех параметров сверяй с исходником; тестовые заглушки не допускаются.

Предпочитай простые типы: bool, byte, uint8_t, int, int16_t, uint16_t, long, unsigned long, int32_t, uint32_t, float, double, char, String. Реальное преобразование и диапазоны проверяй в экспортированном .ubi и итоговом .ino FLProg, особенно для uint16_t, uint32_t, double, String.

Не представляй массивы, объекты классов, struct и указатели как обычные контакты без отдельной проверки. Для параметров используй простые значения по умолчанию соответствующего типа.

FIX14–FIX16 (с сохранением в последующих сборках) — строковые параметры String
При экспорте Code Basic и Code Professional ссылки на параметры String ...; // par в коде setup(), loop() и телах вспомогательных функций преобразуются в локальные объекты String. Это сохраняет методы .c_str() и сравнения строк после подстановки FLProg строкового литерала.

В FIX15 исправлена привязка имён параметров для Code Basic. При проверке итогового .ino убедись, что временные String-объекты ссылаются на реально подставленные параметры, а не на необъявленные идентификаторы. При необходимости используй явное преобразование String(параметр), особенно в нестандартных выражениях. Код глобальных объявлений и необычные случаи требуют отдельной проверки в FLProg 9.8.0.

FIX17 — числовые параметры // par, включая keepAlive:
В MQTT обнаружена ошибка подстановки числового параметра: после экспорта в Code Basic конструкция могла превратиться в «if ( > 0 && <= 65535) ...» или вызов с пустым аргументом «(uint16_t)». FIX17 добавил локальные снимки параметров в секциях функций/setup/loop, например «auto __ino2ubi_numeric_keepAlive = keepAlive;», чтобы условие, приведение типа и аргументы методов использовали корректное C++-выражение. Это делает генератор, а не автор .ino; в скетче оставляй обычное объявление «int keepAlive = 60; // par: Интервал MQTT KeepAlive, с».
Проверяй каждый числовой параметр в итоговом .ino FLProg — в if, сравнениях, приведениях типа, выражениях, вызовах функций и методах; недопустимы пустые операнды, незаменённые имена или некорректные временные переменные. Проверяй имя/подпись/значение, особенно после экспорта обоих форматов. Не исправляй проблему удалением // par, жёсткой подстановкой «60» или переписыванием алгоритма. Учитывай, что нестандартные глобальные выражения и области видимости требуют дополнительной проверки.
Автоматические суффиксы имён вроде «_123773303_1» или «_89153959_1» назначает FLProg; не записывай их в исходный скетч и не рассчитывай на заранее известные суффиксы. При общей интеграции блоков проверяй, что ссылки действительно указывают на один и тот же сгенерированный объект.

4. Code Basic и Code Professional
Code Basic:

создаётся обычный .ubi;
метки // in, // out, // par, // variable должны быть корректно распознаны;
подписи после // par: должны отображаться в настройках блока, при этом C++-имена параметров сохраняются для правильной подстановки.
Code Professional:

создаётся один файл .ubi, без ZIP;
входы, выходы и параметры формируются средствами Professional;
подпись после // par: используется как отображаемое название параметра;
генератор FIX11/FIX12 создаёт новые внутренние идентификаторы при экспорте, чтобы уменьшить риск конфликта «Такой блок уже есть».
Один и тот же блок всё равно нужно отдельно проверять в каждом режиме. Успешная генерация в Basic не гарантирует правильной работы Professional и наоборот.

ОСОБЕННОСТЬ Code Professional — обнаружено в MQTT FIX18–FIX20:
При загрузке Professional .ubi, содержащего отдельную секцию вспомогательных функций, FLProg 9.8.0 несколько раз аварийно завершался на этапе объявления переменных (до компиляции Arduino) со стеком «Arduino.DeclaringElement>>declaringTypeString», «Arduino.DeclaringElement>>declaringString», «Arduino.ArduinoBasicCodeCompiler>>declareBlocks» и сообщением «Message not understood: #declaringString». Переход с глобального конструктора «PubSubClient mqttGlobalClient(espGlobalClient);» на «PubSubClient mqttGlobalClient;» + «mqttGlobalClient.setClient(espGlobalClient);» в setup() сам по себе не устранил эту аварию.
В FIX20 вспомогательные функции в экспортированном Professional .ubi включены вместе с объявлениями в секцию «declare», без самостоятельной секции «function»; конкретный тестовый MQTT-блок с этим изменением успешно скомпилирован. Для будущих блоков это рабочий проверенный на одном примере подход, а не гарантия для любого C++.
При анализе Professional сохраняй все функции и их тела, проверяй порядок #include/объявлений/функций, типы контактов и параметров, ссылки sixx.idref, состав секций, а также реальную компиляцию в FLProg. Не помещай функции в неподходящие места исходного .ino вручную — правила размещения относятся к генератору .ubi. Если FLProg снова падает, не выдавай отчёт Arduino IDE за причину: ошибка произошла раньше, в генерации FLProg. Для диагностики пригодятся экспортированный .ubi, лог error.log и исходный .ino.
Для передачи файлов: основным артефактом Professional остаётся .ubi, но его допустимо упаковать в обычный ZIP, если браузер блокирует скачивание расширения .ubi. Если реально нужны отдельные пользовательские .h/.hpp, их исходники должны быть предоставлены и установлены, а не подменены заглушкой.

5. Правила для #define и библиотек
Не используй пользовательские числовые макросы #define в коде, предназначенном для ino2ubi: они вызывают ошибки анализатора в обоих режимах (например MAX_NUM_CHANNELS и MAX_ONOFF_CHANNELS). Это относится ко всем аналогичным именам, а не только к известным примерам.

Неправильно:

#define LIMIT 12 // par: Предел нагрузки
            
Правильно, если это действительно настраиваемый параметр:

int LIMIT = 12; // par: Предел нагрузки
            
Если значение не должно редактироваться, используй const int или другое типизированное константное объявление, совместимое с контекстом. Не добавляй // variable к #define: это не превращает макрос в переменную. Если значение участвует в размере статического массива, шаблонном параметре или case, требуется константное выражение, а не изменяемая переменная. Для объявлений массивов в этой версии конвертера предпочитай явные числовые размеры (int channels[6];), поскольку парсер может отвергать символьные размеры. Не изменяй значения или количество каналов ради обхода ошибки.
Перед выдачей кода найди каждое применение удаляемого макроса: размеры массивов, границы циклов, индексы, switch/case, условия, структуры, шаблоны и #if. Заменяй последовательно; в #if C++ const/constexpr не заменяют препроцессорные макросы. Не удаляй системные определения библиотек. Не заменяй автоматически любые макросы параметрами: условная компиляция и макросы библиотек имеют другую семантику.

#include <Wire.h>, #include <Preferences.h>, #include "SomeLibrary.hpp" означает подключение библиотеки, а не доказательство её отсутствия в Arduino IDE или FLProg. Сохраняй необходимые #include и проверяй доступность зависимостей при сборке. ino2ubi не имеет доступа к списку библиотек, установленных у пользователя.

В пределах одного .ino не вставляй одинаковый #include <WiFi.h> дважды: оставляй одно подключение, если оно необходимо. При объединении нескольких FLProg-блоков один и тот же #include может повториться в итоговом проекте; это не означает, что Wi-Fi подключается несколько раз: заголовки обычно защищены от повторного включения. Не удаляй необходимый #include из независимого блока только ради отсутствия дублирующего текста. Настоящие конфликты — повторный вызов WiFi.begin(), смена режима WiFi.mode(), отключение WiFi.disconnect(), создание конфликтующих глобальных объектов, дублирующиеся обработчики и владение одним сервисом несколькими блоками. Диагностическое сообщение Arduino IDE «Найдено несколько библиотек для WiFi.h» само по себе не доказывает ошибку; проверяй, какая реализация выбрана для ESP32 Core 2.0.17.

Собственный .hpp не создавай без необходимости и без исходного кода библиотеки. В текущей схеме пользователь не разрабатывает отдельные собственные библиотеки: обычный экспорт — один .ubi. Не придумывай «заглушки» .hpp и не обещай, что конвертер автоматически создаст реализацию новой библиотеки.

6. Ограничения парсера, массивы и функции
Включай обе функции: void setup() { ... } и void loop() { ... }; не добавляй main().
Никогда не ставь return непосредственно в setup() или loop(): код попадает в общий цикл FLProg и может остановить исполнение последующих блоков. Используй if/else и корректное управление состоянием.
return во вспомогательных функциях допустим.
Не используй delay() в основном рабочем коде блока, бесконечные ожидания и долгие блокирующие циклы. При необходимости применяй millis() / micros() с учётом переполнения. При автоматическом поиске delay() отличай настоящий вызов от слова «delay()» внутри начального комментария, справки или строкового литерала: совпадение в комментарии не является исполняемой блокировкой.
Размеры статических C-массивов задавай явными положительными десятичными числами, например bool states[32] = {false}; // variable; избегай [BUFFER_SIZE], [N], [2*16], [], VLA.
Всегда проверяй индексы массива и границы буферов. Для snprintf рассчитывай буфер по максимально возможной длине значений, знакам, разделителям и завершающему нулю: %02d задаёт минимальную ширину, не максимальную. Например, для трёх int16_t в строке времени буфер char buf[12] может вызвать предупреждение; char buf[24] достаточен для этого формата.
Вспомогательные функции оформляй обычными C++-функциями с явными аргументами и типом результата; избегай шаблонов и параметров по умолчанию без проверки.
Осторожно используй условную компиляцию, сложные макросы, классы, перегрузки и нестандартные объявления: парсер может не сохранить их структуру.
Библиотечные объекты вроде Preferences pref; проверяй в секции объявлений и итоговом коде FLProg. Не объявляй локальную переменную с тем же именем, что вход или параметр; учитывай имена формальных аргументов функций. Для объекта с конструктором через аргумент проверь, сохраняет ли конкретный режим экспорт корректно; для MQTT допустим вариант с отдельным setClient() в setup(), однако он сам по себе НЕ исправляет дефект секций Professional.
Метка // variable не гарантирует независимость нескольких экземпляров блока.
Опция En: если в конвертере включён отдельный контакт En, выполнение основной логики может быть обёрнуто в проверку if (En). При En = false выходы и состояние не обязательно сбрасываются сами по себе. Не путай эту опцию с собственным входом bool inEnable; // in. Заранее определяй поведение отключения и повторного запуска.

7. ESP32 Arduino Core 2.0.17
Используй только API, совместимый с Espressif Arduino-ESP32 2.0.17 / ESP-IDF 4.4.7.

Примеры:

ШИМ Core 2.x: ledcSetup(channel, freq, resolution), ledcAttachPin(pin, channel), ledcWrite(channel, duty).
Аппаратные таймеры Core 2.x: timerBegin(index, divider, countUp), timerAttachInterrupt(...), timerAlarmWrite(...), timerAlarmEnable(...).
Приём ESP-NOW Core 2.x: void onRecv(const uint8_t* mac, const uint8_t* data, int len).
Не подменяй их API из Core 3.x, например ledcAttach(...), timerBegin(frequency) или callback с esp_now_recv_info_t.

Если работа связана с GPIO, уточняй модель платы и ограничения конкретных выводов. Учитывай владельцев Wi-Fi, ESP-NOW, Serial, аппаратных таймеров, LEDC-каналов и других общих ресурсов.

8. СЕТЕВЫЕ БЛОКИ: ОБЩИЙ Wi-Fi, MQTT, HTTP, NTP, WebSocket И ДРУГИЕ СЕРВИСЫ
Главное правило: если создаваемый блок пользуется сетью, но не является Wi-Fi-менеджером, он использует УЖЕ установленное ESP32-соединение, которым владеет отдельный системный блок FLProg. Не создавай скрытый второй Wi-Fi-менеджер.

Для клиентских блоков MQTT, HTTP, NTP/SNTP, HTTPS, WebSocket, Telegram и т. п. по умолчанию:
• подключай <WiFi.h> только когда используешь соответствующий API; не создавай копию WiFi.h;
• проверяй WiFi.status() == WL_CONNECTED перед сетевой операцией, но помни, что одно это условие не гарантирует доступность брокера/интернета;
• не вызывай WiFi.begin(), WiFi.mode(), WiFi.disconnect(), WiFi.softAP(), WiFi.config() или WiFi.setHostname() без явного запроса на управление самим Wi-Fi;
• не сохраняй Wi-Fi SSID/пароль повторно в сетевых сервисных блоках, если пользователь этого не просил;
• при потере Wi-Fi выставляй понятные состояния, останавливай/откладывай только собственные операции и возобновляй работу без вмешательства в чужой Wi-Fi;
• не создавай множество одинаковых глобальных объектов/обработчиков с одинаковыми символами, не переопределяй общие callbacks и не переключай чужой сетевой клиент;
• указывай, какие операции блокирующие (MQTT connect, HTTP GET, TLS handshake) и сколько максимум они могут задерживать другие блоки; не обещай полной неблокирующей работы, если библиотека синхронная.

Пример проверки: «if (WiFi.status() == WL_CONNECTED) { /* собственная работа с сервисом */ }».
Исключение: специально запрошенный блок Wi-Fi Manager МОЖЕТ управлять WiFi.begin()/disconnect()/mode(), но должен быть единственным владельцем и иметь явно описанную политику переподключения.

MQTT-архитектура: один MQTT Main Controller отвечает за подключение, reconnect, mqttClient.loop(), setCallback() и общую сессию. Другие блоки публикации/подписки должны использовать согласованный интерфейс владельца, а не создавать конкурирующие независимые MQTT-подключения без требования пользователя. У PubSubClient на один клиент задаётся один активный callback: не перезаписывай его из нескольких блоков. Main Controller в рассмотренном проекте — один экземпляр; его совместимость с другими блоками требует отдельной совместной проверки. Не храни пароли в логах/открытых статусах.
Для NTP/SNTP, ESP-NOW и иных глобальных служб также устанавливай единственного владельца или согласованный диспетчер. Если сервис нельзя безопасно дублировать, явно указывай ограничение одного экземпляра.

9. Несколько экземпляров и NVS
При использовании Preferences, Flash/NVS, Wi-Fi, MQTT, ESP-NOW, callbacks и других глобальных ресурсов проверяй работу нескольких экземпляров блока.

ПРАВИЛО: если код использует Preferences, имя пространства NVS ОБЯЗАТЕЛЬНО объявляй как редактируемый параметр блока:
String nvsNamespace = "sntp_cfg"; // par: Имя пространства памяти NVS
Preferences prefs; // variable
Перед использованием метода c_str() приводи параметр к String при необходимости: String ns = String(nvsNamespace); if (prefs.begin(ns.c_str(), true)) { /* чтение */ prefs.end(); }.
Не используй жёстко прописанное prefs.begin("sntp_cfg", ...) для пользовательского блока с настраиваемой памятью. Имя пространства ограничено 15 символами; проверяй корректность имени и результат begin(). При нескольких экземплярах пользователь должен задать каждому своё имя пространства, например sntp_1 и sntp_2; одинаковое значение по умолчанию само по себе не обеспечивает уникальность. Ключи хранить в выбранном пространстве, не стирать чужие значения. Не писать во Flash на каждом цикле; при смене namespace корректно закрывать прежнее пространство и работать с новым. Разделение NVS не решает конфликтов общих сервисов вроде SNTP и Wi-Fi.
Одинаковый NVS namespace и одинаковые ключи приводят к использованию одних и тех же сохранённых данных.
Разные имена C++-переменных сами по себе не меняют строковые имена namespace.
Не записывай Flash в каждом проходе loop(); записывай только при необходимости.
Для общего callback должен быть определён владелец или механизм диспетчеризации.
Не заявляй о независимости экземпляров, пока не проверены два блока на одной схеме.
Если безопасна только одна копия, включай соответствующее ограничение однократного использования блока и проверяй его в FLProg.
10. Корректность логики
Реализуй именно поведение, которое запросил пользователь. Определи:

стартовое состояние и начальные выходы;
реакцию на изменение параметров и неверные значения;
отличие удерживаемого уровня входа от короткого импульса/фронта;
поведение при повторных, одновременных и пропущенных событиях;
отключение и повторное включение, таймауты и сбои;
переполнение счётчиков и буферов, перезагрузку и сохранение данных.
Не добавляй FIFO, таймеры или автоматы состояний, когда задача этого не требует. Проверяй деление на ноль, типы, переполнения, диапазоны и доступ к памяти.

11. ПРЕДУПРЕЖДЕНИЯ КОМПИЛЯТОРА И ТИПЫ ДАННЫХ (реальный случай Code Basic MQTT)
Пример предупреждения из FLProg/ESP32:
«warning: comparison is always true due to limited range of data type [-Wtype-limits]»
Исходный фрагмент MQTT: «if (inPort > 0 && inPort <= 65535) mainPort = inPort;».
В Code Basic FLProg сгенерировал вход с собственным суффиксом, например «inPort_123773303_1», а компилятор указал, что сравнение «inPort_123773303_1 <= 65535» ВСЕГДА истинно для фактического типа входа. Это предупреждение, не ошибка; скетч продолжил компиляцию.
Правило исправления: если проверено, что тип входа в итоговом .ino НЕ может превышать 65535, упрощай условие до «if (inPort > 0) mainPort = inPort;» — лишняя верхняя проверка не влияет на результат для этого типа. Не изменяй автоматически другие условия без анализа настоящего типа и диапазона. Учитывай, что в обычном ESP32 C++ тип int обычно 32-битный, а отображение контакта FLProg может отличаться: конкретный тип необходимо ПРОВЕРИТЬ в сгенерированном коде.
ВАЖНО: если нужен весь диапазон TCP/UDP портов 1–65535, проверь, что выбранный тип контакта FLProg действительно может представить значения 32768–65535. Если контакт фактически знаковый 16-битный, простое удаление проверки НЕ расширит диапазон. Используй поддерживаемый в FLProg более широкий или беззнаковый тип и явную проверку 1–65535, если это возможно; потом заново проверь экспорт/компиляцию. Не объявляй поддержку всех портов без проверки диапазона.
Не путай предупреждение C++ с тем, что собственный анализатор ino2ubi v2.16 скрывает предупреждения. Оценивай каждое сообщение: значимые предупреждения о сужении, переполнении, форматировании, преобразовании указателей, памяти и неверных сравнениях исправляй, а не маскируй флагами компилятора. Не меняй суффиксы, назначаемые FLProg.

12. Проверка перед выдачей результата
В используемой линейке ino2ubi v2.16 отображаются ошибки, а предупреждения скрыты; отсутствие сообщений не означает, что проверка компиляции и поведения выполнена.

Обязательные этапы:

Проверить короткое название из первой строки комментария, описание, синтаксис, назначение входов/выходов/параметров и обязательные русские подписи // par:; проверить подписи не только в комментарии, но и в настройках блока FLProg.
Проверить отсутствие всех пользовательских числовых #define и необработанных ссылок на них, правильность размеров массивов, опасных return, delay(), переполнений snprintf и скрытых блокировок; при использовании Preferences обязательно проверить параметр имени NVS.
Выполнить «Парсить код» и проверку ошибок ESP32. Если используется «Открыть скетч», проконтролировать, что GPIO не назначены произвольно, а Serial.print/println не превращены в выходы.
Проверить право владения общими сетевыми ресурсами: отсутствие скрытых WiFi.begin()/disconnect() у MQTT/HTTP/NTP-клиентов, единый управляющий MQTT-клиент, корректный callback, поведение при обрыве сети.
Если есть числовые // par, проверить подстановку выражений во всех функциях, включая касты и аргументы вызовов, и отсутствие пустых операндов. Проверить индикацию русских подписей // par: и сохранение их значения.
Если это Code Professional, проверить секции объявления/вспомогательных функций на соответствие отработанному FIX20 и целостность типов/ссылок SIXX.
Экспортировать нужный .ubi и убедиться, что состав и значения параметров корректны.
Импортировать блок в FLProg 9.8.0, проверить его интерфейс, включая русские названия параметров.
Проверить сгенерированный FLProg .ino, затем компиляцию с ESP32 Core 2.0.17. Просмотреть не только ошибки, но и предупреждения C++ (особенно сравнения диапазонов и потери точности), устранять их в исходном скетче, не нарушая семантику.
При сообщениях «#declaringString», «SixxClassNotFound» или крахе при создании кода считать это ошибкой структуры экспорта/внутреннего компилятора FLProg до Arduino; сравнить .ubi с рабочим экспортом и не объявлять исправление успешным по одному XML-парсеру.
При необходимости проверить на физической плате и с двумя экземплярами блока.
Отдельно различай: статическую проверку, успешный экспорт, успешный импорт, компиляцию и реальное испытание. Никогда не называй блок проверенным на плате или успешно скомпилированным, если этого не было.

При ошибках анализируй первую реальную причину по сообщению компилятора и итоговому коду FLProg. Не добавляй обходные функции и слои, маскирующие ошибку архитектуры или владения ресурсами.

Краткая справка и специальные режимы (RemoteXY)

Что делает конвертер

Профиль сборки: ESP32, Espressif Arduino Core 2.0.17 (API 2.x), обычный FLProg 9.8.0. Проверка не заменяет сборку на реальной плате.

ino2ubi преобразует Arduino-скетчи (.ino) в пользовательские блоки (.ubi) для программы FLProg. Блок можно импортировать в FLProg и использовать как обычный пользовательский блок.

Пошаговая инструкция

  1. Загрузите .ino или .i2u.json (кнопка «Открыть файл / проект») или вставьте код Arduino в поле слева.
  2. Нажмите «Парсить код» — конвертер извлечёт переменные и функции и сразу выведет внизу ошибки, их строки и рекомендации по исправлению.
  3. Во вкладках «Переменные» и «Функции» при необходимости отредактируйте настройки (двойной клик по строке).
  4. Задайте название и описание блока.
  5. Нажмите «Сгенерировать .ubi и скачать» — файл сохранится на компьютер.
  6. Импортируйте .ubi в FLProg (меню библиотеки блоков).

Роли переменных

  • variable — внутренняя переменная, не отображается на блоке.
  • input — вход (слева на блоке), получает данные от других блоков.
  • output — выход (справа на блоке), передаёт данные другим блокам.
  • parameter — настраиваемый параметр, задаётся в свойствах блока.

Определение ролей в коде

Роли можно задать комментариями после объявления переменной:

int sensorValue = 0;  // in — вход
int result = 0;       // out — выход
int threshold = 100;  // par — параметр

Для старых файлов поддерживается #define с //par, но числовые #define в профиле FLProg 9.8.0 запрещены: они могут вызвать конфликт имён при генерации.

Подсказки внизу редактора учитывают назначение макроса: для задержки #define MIN_PRD 5000 предлагается 5000UL или unsigned long, а для размеров массивов — конкретная длина в квадратных скобках.

Безопасные массивы FLProg 9.8.0

Не используйте #define BUFFER_SIZE 32, eventState[BUFFER_SIZE] или вычисляемый размер [2*16]. Задавайте длину только числом, например:

static bool eventState[32] = {false}; // variable
static uint32_t eventTime[32] = {0};  // variable
uint8_t bufferSize = 32;             // variable

Для управления логическим пределом используйте отдельную переменную bufferSize и не допускайте значений больше фактической длины массива. Проверка массива выполняется перед экспортом.

Код ESP32 2.0.17

Для ШИМ: ledcSetup(channel, freq, resolution), затем ledcAttachPin(pin, channel) и ledcWrite(channel, duty). Не используйте API 3.x: ledcAttach, timerAlarm, esp_now_recv_info_t.

RemoteXY (экспериментально)

Для Arduino-скетча RemoteXY нажмите «Парсить код» или «Парсить RemoteXY». В «Переменные» появятся контакты FLProg; двойной клик позволяет изменить только подпись контакта. Во вкладке «Функции» отображаются автоматически генерируемые setup() и loop() только для просмотра. Скачивание выполняется исключительно отдельной кнопкой «Сгенерировать .ubi и скачать».

Wi-Fi подключает FLProg; учётные данные из RemoteXY не экспортируются. Один блок RemoteXY на проект. Для работы требуется библиотека RemoteXY 4.1.11.

EEPROM включается автоматически только при наличии специальных отметок «Сохранять в EEPROM» в конфигурации редактора RemoteXY (новый формат 254/V21). Старый формат 255/V19 таких отметок не содержит: включите сохранение для нужных элементов и снова получите Arduino-код в редакторе. EEPROM.h добавляется перед RemoteXY.h, память ESP32 резервируется через EEPROM.begin(). При совместном использовании EEPROM с другими блоками FLProg проверьте занятые адреса и повторную инициализацию.

Старые файлы оригинального конвертера

Поддерживаются .ino/.txt с маркерами // in, // out, // par и // input, // output, // parameter. Чтобы сохранить ручные настройки входов и выходов, используйте «Сохранить проект», затем открывайте .i2u.json.

Примечания

  • Комментарий в начале скетча (// или /* */) используется как описание блока.
  • Функции setup() и loop() автоматически помещаются в соответствующие секции блока.
  • Дополнительные функции отображаются во вкладке «Функции»; тело можно редактировать двойным кликом.
  • Опция «Вход En» оборачивает код в loop в условие if(En) { … } — блок будет выполняться только при активном входе En.
