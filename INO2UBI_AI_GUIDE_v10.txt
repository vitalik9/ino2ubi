СТРОГАЯ ИНСТРУКЦИЯ ДЛЯ ИИ: INO2UBI / FLProg / ESP32
Редакция v10 — 18.11.2026 (Core 2.0.17 по умолчанию, Core 3.3.11 по выбору; внешние Wi-Fi-блоки FLProg)
ЦЕЛЕВАЯ ЦЕПОЧКА: INO2UBI v2.17 RC4 → Code Professional (.ubi) → FLProg 9.8.6 → ESP32 Arduino Core 2.0.17.

ЦЕЛЬ
Создавать не просто синтаксически правильный .ino, а функционально корректный пользовательский блок FLProg, который сохраняет требования пользователя, правильно преобразуется конвертером, не повреждает работу соседних блоков и не конфликтует с периферией. Приоритеты: (1) безопасность технологического алгоритма; (2) достоверность API; (3) совместимость с конвертером; (4) корректность итогового C++; (5) поддерживаемость и ясная документация.

ОБЯЗАТЕЛЬНАЯ ОГОВОРКА ОБ УРОВНЕ ДОСТОВЕРНОСТИ
Правила по формату меток и по библиотекам основаны на предоставленных инструкциях, архиве libraries.zip и пользовательской проверке маркера «Название блока:». Редакция v8 учитывает предоставленную единую сборку ino2ubi-2.17-RC4-unified-radio-static-local-help.zip и подтверждённое пользователем отображение RadioButton в FLProg 9.8.6. Совместимость других конструкций и плат не предполагается автоматически. Это не заменяет фактический импорт .ubi и компиляцию в FLProg. Не заявляй, что конкретная конструкция, библиотека или этап «пройдены», пока не получены соответствующие результаты фактической проверки. Документ снижает риск ошибок, но не гарантирует безошибочность автоматически сгенерированного кода.

2. НЕПРИКОСНОВЕННОСТЬ ТРЕБОВАНИЙ
Перед написанием кода составь для себя контракт блока: назначение, входы/выходы/параметры, их имена, типы, единицы и диапазоны; алгоритм по шагам; реакции на запуск/останов/сброс; таймауты; обработка ошибок; условия аварий; поведение при восстановлении; аппаратная модель; список ресурсов; количество экземпляров и предполагаемое поведение входа En (если он нужен).
Если пользователь уже задал эти сведения, не спрашивай повторно. Не добавляй выдуманных режимов, защит, команд, регистров, адресов, пинов, задержек и функций. Не изменяй технологическую последовательность, инверсию сигналов, значения таймаутов, состояния безопасного отказа или протокол без явного основания. Если отсутствует критически важная информация для безопасного подключения оборудования, задай один конкретный вопрос; для несущественных деталей разрешено явное безопасное допущение, помеченное в описании.
При исправлении ранее рабочего блока сохраняй его публичный интерфейс и семантику, если пользователь не запросил изменения.

3. ОБЯЗАТЕЛЬНЫЙ ФОРМАТ НАЧАЛА .INO: ИМЯ И РУССКОЕ ОПИСАНИЕ
Самые первые содержательные символы файла — комментарий /* ... */ до любого #include или объявления. В ПЕРВОЙ СОДЕРЖАТЕЛЬНОЙ СТРОКЕ ставь ТОЧНЫЙ маркер «Название блока: BlockName»; BlockName — краткое имя на английском латиницей (рекомендуется ASCII, без пробелов и кириллицы; например OnDelayTimer, CounterMain). Пользователь подтвердил, что формат с данным маркером заполняет поле «Название блока»; строка только с именем этого не обеспечивала. НЕ заменяй маркер на @name, @blockName, Name:, // name или имя файла .ino.
После строки названия в ЭТОМ ЖЕ комментарии укажи ПОЛНОЕ описание на грамотном русском языке. Конвертер должен получать текст для поля «Описание блока» из начального комментария. Включай только фактически реализованные возможности. Описание обязано раскрывать:
a) назначение и применимость блока;
b) последовательность работы, запуск, останов, сброс и повторный запуск;
c) каждый вход: точное C++ имя, тип, уровень активности, назначение, единица;
d) каждый выход: имя, тип, значение в норме, при остановке и при ошибке;
e) каждый параметр: имя, тип, допустимый диапазон, единица, значение по умолчанию, эффект изменения; если есть choices:, перечисли все подписи и их числовые значения;
f) ошибки, таймауты, граничные случаи и восстановление, если предусмотрены;
g) внешние библиотеки, оборудование, периферию и требования к подключению;
h) ограничения, наличие/отсутствие поддержки нескольких экземпляров.
Не добавляй в пользовательское описание недоказанные утверждения вроде «проверено на ESP32», «полностью совместимо со всеми платами» или «безопасно для нескольких экземпляров». После изменения кода актуализируй описание. Нельзя выдавать описание только отдельным текстом в чате — оно обязательно внутри исходного .ino.

ОБРАЗЕЦ ЗАГОЛОВКА (это образец оформления, а не доказательство поддержки любого алгоритма):
/*
Название блока: OnDelayTimer

Назначение: задержка включения дискретного выхода.
Алгоритм: при Enable=true отсчитывается DelayMs; по завершении Ready=true.
При Enable=false Ready=false, отсчёт начинается заново при следующем включении.
Вход: Enable (bool) — разрешение, активный уровень true.
Выход: Ready (bool) — завершение задержки; при выключении false.
Параметр: DelayMs (uint32_t) — задержка в мс, по умолчанию 3000.
Библиотеки: Arduino.h; дополнительные библиотеки не требуются. Wi-Fi обслуживают внешние блоки FLProg, если он используется в схеме.
Аппаратные ресурсы: GPIO, UART, сеть и аппаратные таймеры не используются.
Экземпляры: предполагается независимость простой логики; проверять два блока в FLProg.
*/

4. ОСНОВНОЙ ФОРМАТ C++ ДЛЯ КОНВЕРТЕРА
После начального комментария используй #include <Arduino.h>, необходимые дополнительные include, простые явные глобальные объявления, void setup() и void loop(). Метку размещай на ТОЙ ЖЕ СТРОКЕ, что объявление:
- // in — вход от схемы FLProg, код блока не должен его сам перезаписывать;
- // out — выход, который код блока устанавливает в определённых условиях;
- // par: Русская подпись — редактируемый параметр FLProg; допускаются отдельные секции | description: Текст описания и | choices: значение=Подпись; ...;
- // variable — внутреннее сохраняемое состояние.

4.1. НАЗВАНИЕ И ОТДЕЛЬНОЕ ОПИСАНИЕ ПАРАМЕТРА (ДОРАБОТАННЫЙ INO2UBI)
Метка // par: на строке объявления создаёт редактируемый параметр. Текст сразу после par: до следующей служебной секции становится русской подписью параметра в свойствах FLProg. Не ограничивай подпись латинским именем C++-переменной.
Для индивидуальной справки параметра используй отдельную секцию | description: с непустым текстом. Исправленный конвертер переносит этот текст в поле description параметра экспортируемого Code Professional .ubi. Это НЕ то же самое, что начальное общее «Описание блока»: оба текста нужны, если пользователь просит полноценную справку.

ПРИМЕР:
float bedLengthM = 4.0f; // par: Длина грядки, м | description: Длина всей грядки для расчёта площади осадков и увлажняемой полосы.
float bedWidthM = 1.0f; // par: Ширина грядки, м | description: Полная ширина грядки для учёта дождя; для испарения используется ширина увлажнения.

ПРИМЕР С RADIOBUTTON (оба порядка допустимы):
uint8_t Mode = 1; // par: Режим | choices: 0=Выключено; 1=Авто | description: Выберите режим работы.
uint8_t Mode = 1; // par: Режим | description: Выберите режим работы. | choices: 0=Выключено; 1=Авто

Правила:
a) метка // par: и секции находятся на одной строке с типизированной переменной и корректным значением по умолчанию;
b) разделители служебных секций должны быть именно « | description: » и « | choices: »;
c) порядок секций description: и choices: допускается любой; если choices: отсутствует, параметр остаётся обычным полем ввода;
d) старый синтаксис // par: Русская подпись без description: продолжает работать, но индивидуальная справка остаётся пустой;
e) описание не изменяет C++-имя, тип, значение по умолчанию или расчётный алгоритм;
f) применяй description: только к // par:, а не к // in, // out или // variable;
g) для справки каждого параметра готового POLIVPOETO добавь description: в каждое из его 12 объявлений, не ограничивайся общим комментарием;
h) после экспорта открой .ubi в FLProg и убедись, что описание видно в свойствах; успешный разбор JavaScript сам по себе этого не доказывает.

Не подменяй редактируемые параметры #define, constexpr, массивами конфигурации или скрытыми литералами. Не записывай значения в // in. Для всех выходов определи начальные, рабочие и аварийные состояния. Для всех // variable определи необходимость инициализации и сброса.
Избегай сложных инициализаторов, шаблонов, глобальных ссылок/указателей, нетривиальных классов, массивов объектов и функций с неоднозначным синтаксисом, пока их поддержку не подтвердили для RC4. Простые глобальные одномерные массивы встроенных типов поддержаны в определённых формах, но ограничения описаны в разделе 10. Несколько объявлений в строке могут обрабатываться, однако для надёжного преобразования предпочтительны отдельные объявления. Вспомогательные функции возможны, но их объявления, прототипы, вызовы и переименование нужно проверить в итоговом C++.

5. ПРАВИЛА ВЫДАЧИ КОДА
По умолчанию выдай один ПОЛНЫЙ самодостаточный .ino (в одном cpp-блоке либо файлом .ino). Никаких «...», псевдокода, недописанных участков, TODO вместо обязательной логики, скрытых внешних определений и вымышленных методов библиотек. Не вставляй демонстрационный nullptr как рабочее подключение исполнительного устройства, UART, PWM или Modbus.
Если требуется код на основании имеющегося проекта, сначала изучи точные доступные исходники и версии библиотек. Если их нет, не выдавай предположительный сложный API за проверенный: реализуй надёжно известную часть и обозначь, что требует проверки в целевом окружении.
После кода кратко перечисли интерфейс блока, зависимости, владение аппаратными ресурсами, рекомендуемый режим галочки нескольких экземпляров, необходимое поведение En и ФАКТИЧЕСКИ проведённые проверки.

6. МОДЕЛЬ ПЛАТЫ И СОВМЕСТИМОСТЬ ESP32
ESP32, ESP32-S2, ESP32-S3, ESP32-C3, ESP32-C6, ESP32-H2 отличаются количеством ядер, наличием Wi-Fi/BLE/Bluetooth Classic, доступными пинами, ADC, PWM, UART, USB, памятью и ограничениями прерываний. Не предполагай, что конкретный GPIO свободен, что Core 1 существует, что все ESP32 поддерживают Bluetooth Classic или что выбранная библиотека поддерживает любую из них. Для работы с железом учитывай схему платы, питание, напряжения, уровни логики, boot/strapping pins, Flash/PSRAM, watchdog и резервы периферии. Для чисто вычислительного блока не требуй модель чипа без нужды.

6А. ESP32 ARDUINO CORE 2.0.17 — ОБЯЗАТЕЛЬНЫЙ СПРАВОЧНИК API (ЯДРО ПО УМОЛЧАНИЮ)
Целевое ядро: Arduino-ESP32 2.0.17 (ESP-IDF 4.4.x, FreeRTOS из ядра). Для задач, где нужны системные API, используй соответствующие стандартные библиотеки этого ядра (это перечень доступных средств, а НЕ указание включать их все): Arduino.h, WiFi.h, WiFiClient.h, WiFiClientSecure.h, WiFiUdp.h, WebServer.h, HTTPClient.h, esp_now.h, Wire.h, SPI.h, Preferences.h, LittleFS.h/FS.h, SPIFFS.h, BLEDevice.h (+BLEUtils/BLEServer/BLEScan), BluetoothSerial.h (только классический ESP32), HardwareSerial, Ticker.h, ESPmDNS.h, Update.h, DNSServer.h, SD.h, driver/i2s.h, esp_task_wdt.h, esp_timer.h, FreeRTOS (xTaskCreatePinnedToCore, очереди, семафоры, мьютексы). Сторонние библиотеки добавляй только при необходимости и с явной пометкой.
Конвертер при выбранном Core 2.0.17 проверяет код статически и ОТКЛОНЯЕТ API ядра 3.x. Не используй ничего из «ЗАПРЕЩЕНО».

6А.1 ШИМ (LEDC) — канальная модель Core 2.x
ledcSetup(uint8_t channel, uint32_t freq, uint8_t resolution_bits);  // возвращает реальную частоту
ledcAttachPin(uint8_t gpio, uint8_t channel);
ledcWrite(uint8_t channel, uint32_t duty);   // ПЕРВЫЙ АРГУМЕНТ — КАНАЛ, не GPIO
ledcRead(channel), ledcWriteTone(channel, freq), ledcWriteNote(channel, note, octave), ledcDetachPin(gpio).
Каналы ESP32: 0–15; у S2/S3/C3 меньше — проверь модель чипа. Один канал — одна частота и разрешение для всех подключённых к нему пинов. ledcSetup/ledcAttachPin вызывай один раз в setup(), а не в каждом проходе loop(). Максимум duty = (1 << resolution_bits) - 1.
Пример:
const uint8_t PWM_CH = 0;
void setup() { ledcSetup(PWM_CH, 5000, 8); ledcAttachPin(2, PWM_CH); }
void loop() { ledcWrite(PWM_CH, 128); }
ЗАПРЕЩЕНО (Core 3.x): ledcAttach(), ledcAttachChannel(), ledcDetach(), ledcOutputInvert(), ledcFade*(), rgbLedWrite().
Встроенный RGB-светодиод: neopixelWrite(pin, r, g, b).

6А.2 Аппаратные таймеры — сигнатуры Core 2.x
hw_timer_t* timerBegin(uint8_t timerIndex, uint16_t divider, bool countUp);   // 3 аргумента; база 80 МГц, divider 80 = 1 МГц
void timerAttachInterrupt(hw_timer_t* t, void (*fn)(), bool edge);              // 3 аргумента
void timerAlarmWrite(hw_timer_t* t, uint64_t ticks, bool autoreload);
timerAlarmEnable(t); timerAlarmDisable(t); timerEnd(t); timerRead(t); timerWrite(t, value); timerStart(t); timerStop(t).
ISR помечай IRAM_ATTR; в ISR нельзя вызывать Serial, delay, new/malloc, WiFi; общие переменные — volatile; критические секции — portMUX_TYPE и portENTER_CRITICAL_ISR/portEXIT_CRITICAL_ISR.
ЗАПРЕЩЕНО (Core 3.x): timerBegin(frequency) с одним аргументом, timerAlarm(), timerAttachInterrupt(t, fn) с двумя аргументами.
Аппаратных таймеров мало (4 на ESP32), два экземпляра блока не получают независимых таймеров — для обычных интервалов используй millis().

6А.3 Wi-Fi и сеть — ВНЕШНИЕ БЛОКИ FLProg (ОБЯЗАТЕЛЬНО)
В целевой архитектуре данного проекта Wi-Fi создаётся, настраивается, подключается и обслуживается ВНЕШНИМИ штатными блоками схемы FLProg, а НЕ пользовательским блоком Code Professional (.ubi), создаваемым INO2UBI. Под «внешними» здесь понимаются отдельные блоки FLProg вне генерируемого пользовательского блока, а не сторонние Arduino-библиотеки.
По умолчанию пользовательский .ubi-блок НЕ владеет Wi-Fi, не вызывает WiFi.mode(), WiFi.begin(), WiFi.disconnect(), WiFi.onEvent(), не выполняет reconnect, не создаёт WiFiServer/WebServer и не открывает повторно уже занятые сетевые соединения. Нельзя добавлять эти вызовы «для надёжности» и нельзя повторно инициализировать Wi-Fi в setup() или loop().
Обмен статусом подключения, IP-адресом, командами и данными проектируй через явно согласованные входы/выходы FLProg либо уже существующий интерфейс сетевого блока. Не придумывай названия портов, типы данных, функции доступа к объектам FLProg или API взаимодействия, если их нет в исходниках и ТЗ. Нет подтверждённого интерфейса — укажи зависимость и границу интеграции, но не вставляй самостоятельную инициализацию.
Для Core 2.0.17 штатные библиотеки WiFi.h, WiFiClient.h, WiFiClientSecure.h, WiFiUdp.h, WebServer.h и HTTPClient.h доступны в составе ядра; их наличие НЕ означает, что они должны подключаться к каждому .ubi-блоку. Встраивай #include только когда пользовательскому блоку действительно разрешено использовать конкретный API, проверен владелец ресурса и это не дублирует внешний блок. Классы Network*, NetworkClient, NetworkUDP и заголовки Network.h/NetworkClient.h относятся к Core 3.x и не применяются в режиме 2.0.17.
При явном отдельном требовании сделать специализированный сетевой пользовательский блок сначала согласуй изменение владельца сети и ответственность за инициализацию, события, reconnect, клиент/сервер, TCP-порт и время ожидания; только после этого применяй API выбранной версии ядра. TLS без проверки сертификата не включай автоматически.

6А.4 ESP-NOW (esp_now.h из ядра 2.0.17)
Приём:    void onRecv(const uint8_t* mac, const uint8_t* data, int len);          // esp_now_register_recv_cb(onRecv)
Отправка: void onSent(const uint8_t* mac, esp_now_send_status_t status);          // esp_now_register_send_cb(onSent)
ЗАПРЕЩЕНО: esp_now_recv_info_t, esp_now_send_info_t, библиотека ESP32_NOW.h / ESP_NOW_Peer (это Core 3.x).
Если ESP-NOW явно предусмотрен отдельным внешним блоком, пользовательский .ubi-блок не должен повторно вызывать WiFi.mode() или esp_now_init(). Для специально согласованного блока-владельца ESP-NOW порядок инициализации: выбор режима Wi-Fi → esp_now_init() → регистрация колбэков → esp_now_add_peer(&peerInfo); согласуй сосуществование с внешним Wi-Fi-блоком и не изменяй его режим автоматически. В колбэке не выполняй тяжёлую работу; обработку переноси в loop().

6А.5 Watchdog, АЦП и прочее
esp_task_wdt_init(uint32_t timeout_s, bool panic);  // 2 аргумента; esp_task_wdt_config_t в 2.0.17 НЕ СУЩЕСТВУЕТ.
Доступны analogRead, analogReadResolution, analogSetAttenuation, analogSetPinAttenuation, analogReadMilliVolts. ADC2 недоступен при активном Wi-Fi (классический ESP32).
hallRead() — только классический ESP32 (на S2/S3/C3/C6 отсутствует). temperatureRead() доступна.
Serial.begin(baud, config, rxPin, txPin) — стандартный вызов UART. SET_LOOP_TASK_STACK_SIZE доступен в Core 2.0.17; менять размер стека следует с учётом общего окружения FLProg.
Wire.begin(sda, scl[, freq]); SPI.begin(sck, miso, mosi, ss); Preferences/NVS и Flash не писать в каждом проходе loop().
BLE (BLEDevice.h): BLECharacteristicCallbacks::onWrite использует std::string (в Core 3.x — String). BLE-колбэки конвертер в FLProg-блок не переносит — отказ с диагностикой.
I2S: driver/i2s.h (i2s_driver_install, i2s_set_pin); ESP_I2S.h — Core 3.x, запрещён. Zigbee.h, Matter.h, ESP_SR.h — Core 3.x, запрещены.

6А.7 ЧЕКЛИСТ ИИ ПЕРЕД ВЫДАЧЕЙ (Core 2.0.17)
- Нет API и заголовков из «ЗАПРЕЩЕНО» и из левого столбца таблицы 6А.6.
- ledcWrite получает номер КАНАЛА; ledcSetup и ledcAttachPin вызваны один раз.
- timerBegin (3 арг.), timerAttachInterrupt (3 арг.), timerAlarmWrite + timerAlarmEnable.
- Колбэки ESP-NOW с сигнатурой (const uint8_t* mac, ...).
- Только реально необходимые стандартные библиотеки ядра 2.0.17; каждый #include указан явно.
- Нет блокирующих delay()/ожиданий сети в loop(); Wi-Fi обслуживают внешние блоки FLProg; пользовательский блок не дублирует их инициализацию.
- Заявляй только фактически выполненные проверки: статическая проверка конвертера не заменяет компиляцию в FLProg.

6Б. ГРАНИЦА ОТВЕТСТВЕННОСТИ ВНЕШНИХ Wi-Fi-БЛОКОВ И .UBI
а) внешние Wi-Fi-блоки FLProg отвечают за конфигурацию сети, запуск, подключение, статус, повторное соединение и уже созданные сетевые объекты;
b) пользовательский блок INO2UBI отвечает только за собственную логику, обработку явно предоставленных входных сигналов и формирование выходов;
c) сетевые данные передаются через подтверждённый контракт интерфейсов, а не через вымышленные глобальные переменные или методы;
d) подключение стандартной библиотеки WiFi.h само по себе не создаёт дополнительный блок FLProg и не даёт права переинициализировать общий Wi-Fi;
e) внешние блоки в данном разделе — отдельные элементы схемы FLProg, тогда как внешние Arduino-библиотеки — отдельная категория программных зависимостей;
f) если нужный функционал не обеспечивается внешними блоками, сначала явно опиши недостающий интерфейс и согласуй архитектуру, не меняй сетевой стек молча.
При экспортировании .ubi не требуй от конвертера автоматически генерировать Wi-Fi-блоки, которые не представлены в его исходном проекте. Работу Wi-Fi следует проверять в составе всей схемы FLProg, а не по одному .ubi. Данное правило одинаково для Core 2.0.17 и 3.3.11.

7. ВЫПОЛНЕНИЕ В ОБЩЕМ FLPROG LOOP
Нельзя использовать return прямо из пользовательских setup()/loop(): при встраивании в общие функции это может пропускать другие блоки. Допустим return из самостоятельной вспомогательной функции. Нельзя использовать бесконечные циклы ожидания, длинные delay(), ожидание сети без таймаута и повторную инициализацию оборудования в каждом проходе. По умолчанию используй неблокирующие состояния и millis(), сравнение unsigned (uint32_t)(now - previous) >= interval. Для больших интервалов и часов продумывай переполнение, для изменения параметров во время отсчёта определяй явную семантику. Не блокируй основной цикл Flash/NVS-записью и сетевыми ожиданиями.

8. ДЕТЕРМИНИРОВАННОСТЬ И ОТКАЗОУСТОЙЧИВОСТЬ
Для каждого выхода и состояния проверь: первый запуск; ложный/истинный вход; фронты и удержание; нулевая/максимальная задержка; повторные команды; быстрое включение-выключение; потеря связи; таймаут; повторное подключение; перезагрузка; переполнение счётчиков; некорректный параметр. Исключи деление на ноль, обращение вне диапазона массива, использование неинициализированных данных, переполнение знаковых типов и небезопасную конверсию. Не добавляй автоматическое повторное включение исполнительного механизма после аварии, если это не предусмотрено ТЗ. Если состояние опасно для оборудования, требуются явные безопасные значения выходов и аппаратные защиты; программный код не подменяет независимые аппаратные цепи безопасности.

9. ТИПЫ, ЧИСЛА, ПАРАМЕТРЫ
Используй однозначные типы фиксированной ширины (uint8_t, uint16_t, uint32_t, int32_t и т.д.), bool, float/double когда необходимо. Следи за диапазонами, знаком, переполнением, литералами UL/U, размером буферов, проверкой NaN/Inf там, где они возможны. bool — true/false. String, большие буферы и динамическая память применяй только с проверкой поддержки парсера и ресурсов ESP32. Не скрывай ошибку параметра подстановкой нуля. Если параметр меняется во время работы, явно определи, применяется он немедленно или при следующем запуске.


9.1. ВЫБОР ОДНОГО ЗНАЧЕНИЯ РАДИОКНОПКОЙ В ГОТОВОМ БЛОКЕ FLProg (RadioButton)
Для параметров с несколькими заранее определёнными значениями в актуальной единой сборке RC4 поддерживается выбор ОДНОГО значения переключателем-кружочком в окне «Параметры» уже импортированного блока FLProg 9.8.6. Это НЕ выпадающий список в интерфейсе конвертера и НЕ несколько независимых галочек. Радиокнопки взаимно исключают друг друга. Пользователь подтвердил видимость такого управления в FLProg на тестовом блоке.

ТОЧНЫЙ СИНТАКСИС исходного объявления на ОДНОЙ СТРОКЕ:
uint8_t Mode = 1; // par: Режим работы | choices: 0=Выключено; 1=Автоматически; 2=Вручную

Строго соблюдай требования:
a) параметр должен быть реальной C++-переменной с начальным значением и меткой // par: в той же строке объявления;
b) после подписи поставь литеральный разделитель « | choices: » без изменения ключевого слова choices;
c) варианты запиши как «значение=Читаемая подпись» и раздели точкой с запятой; требуется минимум два варианта;
d) начальное значение C++ должно присутствовать среди значений choices: и определяет вариант, выбранный по умолчанию;
e) каждый вариант должен иметь уникальное значение, понятную непустую подпись и тип, совместимый с типом переменной;
f) числовые значения используются в коде Arduino C++, подписи используются только в свойствах блока FLProg; не сравнивай переменную с текстом подписи;
g) не создавай вручную UUID, XML, UserCodeMultiBlockRadioButtonParametrSpecies или дополнительные булевы входы для каждого режима;
h) не используй choices: в // in, // out, // variable и в произвольном комментарии: это описание допустимых вариантов именно параметра // par:;
i) если список допустимых значений не задан, применяй обычный // par: с полем ввода и не выдумывай варианты;
j) не обещай множественный выбор: RadioButton позволяет выбрать только один вариант.

ПОЛНЫЙ МИНИМАЛЬНЫЙ ПРИМЕР .ino:
/*
Название блока: ModeSelectorDemo
Назначение: демонстрация выбора одного режима работы в свойствах блока FLProg.
Параметр: Mode (uint8_t) — 0 выключено, 1 автоматически, 2 вручную; по умолчанию 1.
Выход: SelectedMode (uint8_t) — числовое значение выбранного режима.
Библиотеки: Arduino.h; внешних зависимостей нет.
Аппаратные ресурсы: не используются.
*/
#include <Arduino.h>
uint8_t Mode = 1; // par: Режим работы | choices: 0=Выключено; 1=Автоматически; 2=Вручную
uint8_t SelectedMode = 0; // out
void setup() { SelectedMode = Mode; }
void loop() { SelectedMode = Mode; }

ПРОВЕРКА РЕЗУЛЬТАТА: после парсинга убедись, что Mode распознан как параметр, затем экспортируй Code Professional .ubi и открой параметры импортированного блока в FLProg 9.8.6. Должны отображаться три переключателя с подписями, и первоначально должен быть выбран «Автоматически». Если значение по умолчанию не включено в choices: либо есть дубли, исправь исходный .ino, а не отключай проверки. Действительно выбранное значение проверяй в генерируемом C++ и по поведению блока. Формат RadioButton подтверждён для проверенного варианта RC4/FLProg 9.8.6, но не для любых версий/типов параметров.

При необходимости отдельного описания RadioButton добавляй | description: Текст в то же объявление, перед или после | choices:; не размещай его вместо choices:.

9.2. ТИПИЧНЫЕ ОШИБКИ, КОТОРЫЕ ИИ НЕ ДОЛЖЕН ДОПУСКАТЬ
НЕПРАВИЛЬНО: uint8_t Mode = 1; // par: Режим работы (0, 1, 2)
Причина: текст в скобках не создаёт переключатели.
НЕПРАВИЛЬНО: uint8_t Mode = 1; // par: Режим работы | choices: Автоматически; Вручную
Причина: нет формата значение=Подпись и отсутствуют числовые значения.
НЕПРАВИЛЬНО: uint8_t Mode = 4; // par: Режим | choices: 0=Выкл; 1=Авто
Причина: значение по умолчанию 4 отсутствует в списке.
ПРАВИЛЬНО: uint8_t Mode = 1; // par: Режим | choices: 0=Выкл; 1=Авто

9.3. ПРАВИЛО ДЛЯ GPT, CLAUDE, GEMINI И ДРУГИХ МОДЕЛЕЙ
Выполняй эту инструкцию как буквальный контракт на формат .ino, а не как свободные рекомендации. Не подменяй нужные конструкции похожими. В частности: «несколько значений параметра» означает фиксированный выбор одного значения RadioButton в ГОТОВОМ блоке; «несколько экземпляров» означает отдельную галочку конвертера; «En» означает отдельный вход, ограничивающий выполнение loop. Это три разные функции. Не придумывай параметры GUI, XML-структуры, метки или библиотеки, которых нет в указанной версии. Если запрос пользователя не содержит варианты параметра, не выдумывай их. Если требуется выбор нескольких вариантов одновременно, не применяй RadioButton без согласования — он является одновыборным контролом. Перед ответом проверь буквальное совпадение синтаксиса с образцом, сохранность типизации и начального значения, а также отсутствие ложных заявлений о фактически не проведённых проверках.

10. РЕЖИМЫ ЭКЗЕМПЛЯРОВ, UUID И ВХОД En (RC4)
10.1. ГАЛОЧКА «Использовать блок несколько раз в одном проекте FLProg»
- по умолчанию снята при новом проекте, после очистки и при открытии старого проекта без сохранённого поля;
- снята: экспорт задаёт isUseItOnce = True; блок ограничен одним размещением в проекте FLProg; проверки, нужные исключительно для независимости экземпляров, не должны выдавать ложные ошибки;
- установлена: экспорт задаёт isUseItOnce = False; включаются дополнительные проверки независимости состояния и предупреждения о совместном доступе к ресурсам;
- сохранённое значение галочки должно восстанавливаться без самопроизвольной смены режима.
Не требуй от пользователя переписывать исходный .ino исключительно потому, что в коде уже предусмотрена многократная работа: при снятой галочке такой код допустим, если проходит остальные проверки. Не выдавай «совместим с несколькими экземплярами» только на основании флага XML.

10.2. ОБЯЗАННОСТИ ИИ И КОНВЕРТЕРА
ИИ пишет алгоритм и описывает, предполагается ли повторное размещение блока, но НЕ вставляет фиксированные UUID-суффиксы в C++. Переименование поддерживаемых сущностей выполняет INO2UBI RC4. У каждого экземпляра должны быть независимыми изменяемые переменные и массивы состояния; вспомогательные функции и ссылки на них проверяются по итоговому C++. Не предполагай автоматическую поддержку произвольных указателей, шаблонов, классов, callback, объектов периферии и разделяемых ресурсов. В последней RC4 поддерживается UUID-изоляция простых глобальных и локальных static-переменных, а также части простых static-массивов; это не распространяется автоматически на произвольные static-объекты, callbacks и constexpr/inline/thread_local. В режиме одного экземпляра не следует выдавать ложную ошибку изоляции на допустимый код.

10.3. ГЛОБАЛЬНЫЕ МАССИВЫ В RC4
RC4 предусматривает UUID-изоляцию простых одномерных глобальных массивов поддерживаемых встроенных типов, например int values[10] = {0};, float temperatures[5]; и bool states[8]; обращения переименовываются в setup(), loop(), поддерживаемых вспомогательных функциях и инициализаторах. Сохраняй элементный тип, размер и начальные значения. Не считай автоматически поддержанными сложные static-массивы, массивы объектов (например Servo s[2]), массивы указателей, 64-битные элементы, размеры без числового литерала (например [] и [N]), повторные объявления и конфликты имён с функцией, #define или иной переменной. Эти ограничения относятся прежде всего к режиму многократного использования; фактическую диагностику проверяй для выбранного режима. Не подменяй массив другим алгоритмом ради обхода диагностики без согласования.

10.4. ГАЛОЧКА «Вход En (условие выполнения кода в Loop: if(En))»
- установлена: генератор создаёт логический вход En и выполняет пользовательский код loop() внутри if (En);
- снята: дополнительный вход En и обёртка if (En) не создаются;
- setup() выполняется при инициализации и не зависит от En;
- при En=false код loop() не выполняется, но выходы и внутреннее состояние автоматически не сбрасываются;
- имя En не должно конфликтовать с уже объявленными сущностями; при необходимости пользовательская логика остановки или безопасного состояния должна быть явно предусмотрена и проверена.
Не добавляй вручную ещё одну обёртку if(En) только из-за включённой галочки. Если технологический алгоритм требует сброса выходов при выключении, согласуй это с пользователем: автоматическое блокирование loop() само по себе такого сброса не обеспечивает.

10.5. ЧЕТЫРЕ СОЧЕТАНИЯ НАСТРОЕК И ФИЗИЧЕСКИЕ РЕСУРСЫ
Независимо проверяй «один/несколько экземпляров» × «En выключен/включён». В многократном режиме ожидай предупреждений о Wi-Fi, BLE, ESP-NOW, I2C/SPI, Serial, EEPROM, таймерах/LEDC и других разделяемых ресурсах: предупреждение не равно запрету, но требует архитектурного решения о владельце. UUID обеспечивает изоляцию имён, а не независимость физического GPIO, UART, TCP-порта или таймера. При повторном использовании обязательно проверь два экземпляра с разными входами и параметрами в итоговом C++ и, если возможно, непосредственно в FLProg.

11. БИБЛИОТЕКИ: СТРОГИЙ ВЫБОР
Для каждой функциональной задачи сначала реши, нужна ли внешняя библиотека вообще. Простая логика, таймеры millis(), счётчики и автоматы состояния должны по возможности работать на Arduino.h. Для специальных задач пользуйся приложением А, но НЕ подставляй классы по названию папки. Перед применением библиотеки необходимо:
a) найти реально существующий заголовок и точные определения класса, конструктора, методов, enum и callback в соответствующей версии;
b) проверить прямые и транзитивные зависимости и доступность всех include;
c) проверить architecture guards и применимость конкретно к ESP32 Core 2.0.17 и выбранной плате;
d) проверить кто уже владеет транспортом, пином, таймером, ISR, сервером или глобальным объектом;
e) проверить жизненный цикл — однократное создание, init, вызовы tick/poll/loop, shutdown и таймауты;
f) проверить совместимость нескольких экземпляров и итоговое переименование объектов;
g) исключить неиспользуемые include и недокументированные методы.
Отсутствие нужной библиотеки в доступной среде — блокирующая зависимость, которую нельзя маскировать заглушкой. Файл в libraries.zip доказывает только наличие файла в архиве, но не установку и не успешную сборку.

12. ЧАСТНЫЕ ТЕХНИЧЕСКИЕ ОГРАНИЧЕНИЯ
Flprog_HardwareTimer: согласно предоставленным сведениям на ESP32 встречается общий hw_timer_t и общий callback; нельзя обещать отдельный независимый таймер каждому блоку. Сверяй настоящий API initFlprogSystemTimer(...) и setFlprogSystemTimerTickPeriod(...), единицы периода и безопасность ISR.
Flprog_HardwarePWM: согласно исходному описанию класс FlprogHardwarePwmPin использует программное формирование через регулярные tick(); одного pwmWrite() недостаточно. Для аппаратного PWM на ESP32 Core 2.0.17 используй LEDC API из раздела 6А (ledcSetup/ledcAttachPin/ledcWrite по каналу) и конфликты каналов/пинов.
Flprog_Modbus: ModbusRTU — абстрактная база в рассмотренном описании; не создавай её экземпляр. Используй конкретный master/slave с действительным UART executor или TCP-транспортом, согласно исходникам. nullptr не заменяет физический канал.
FLProg_Network: сетевая библиотека может использоваться внешними блоками FLProg, но её наличие не требует включения flprogNetwork.h в пользовательский блок. В данном проекте владелец Wi-Fi — внешние блоки FLProg; дополнительные MQTT/TCP/UDP/OTA-блоки обязаны согласовать общий ресурс без повторной инициализации.
RT_HW: если библиотеке необходимы schedulers, tick(), poll() или аппаратная обёртка, явно подключай их и обеспечивай своевременное выполнение. Наличие API без обслуживания не равно работающей периферии.
ESP32 Core 2.0.17 (по умолчанию): используй API раздела 6А; API ядра 3.x (ledcAttach, timerAlarm, Network*) не переносить.

13. CALLBACK, ISR, FREERTOS
Проверяй сигнатуры и все места использования callback как указателя на функцию. ISR должны быть короткими: никакого Serial, Wi-Fi, тяжёлой обработки, блокирующей синхронизации и динамического выделения. Данные, общие для ISR/задач/loop, защищай соответствующими атомарными операциями либо критическими секциями; volatile не равнозначен потокобезопасности. Не создавай FreeRTOS-задачу при каждом вызове loop; контролируй создание, стек, watchdog, блокировки и завершение. Не запускай задачу на несуществующем ядре ESP32-C3.

14. GPIO / ПРОТОКОЛЫ / ИСПОЛНИТЕЛИ
GPIO: определяй направление, активный уровень, подтяжки, электрические пределы, стартовое состояние и конфликт с FLProg. PWM: указывай частоту, разрядность, пин, границы duty и драйвер. UART/RS485/Modbus: указывай baud, parity, stop bits, DE/RE, slave ID, register map, порядок байтов/слов, таймауты, retry, запрет параллельных запросов. I²C/SPI: адреса/CS, частоты, общую шину и её владельца. MQTT: клиент ID, топики, QoS, reconnect с backoff, сетевые таймауты, не блокировать loop. Flash/NVS/EEPROM: ограничивать частоту записи и предусмотреть повреждение данных. Нельзя выдумывать адреса Modbus или формат внешнего устройства.

15. ДИАГНОСТИКА И ЧЕСТНОСТЬ ПРОВЕРОК
Тесты RC4 проверяют экспорт, флаги, изоляцию простых массивов и синтаксис генерируемого C++, но не подтверждают сборку в реальном FLProg. Устаревшие или не запущенные браузерные/ BLE-тесты отмечай отдельно, не смешивая их с ошибками генерации. Разделяй уровень проверки: А — экспертный просмотр текста; Б — успешный парсинг и проверка INO2UBI; В — успешный экспорт .ubi; Г — импорт в FLProg и анализ итогового C++; Д — успешная компиляция Core 2.0.17 на точной плате; Е — испытание на реальном устройстве; Ж — тест двух экземпляров и совместимости с другими блоками. Указывай только реально выполненные уровни. Ошибка, предупреждение и информационное сообщение — разные сущности; не глуши диагностику ради «0 ошибок». При неудаче приводи сообщение, причину и минимальную правку. Нельзя объявлять компиляцию «проверенной», если была проверена только синтаксическая форма .ino.

КРИТИЧЕСКИЕ НАБЛЮДЕНИЯ ИЗ ИСХОДНИКОВ АРХИВА
- Flprog_HardwarePWM/src/flprogHardwarePwm.h прямо описывает программный PWM: FlprogHardwarePwmPin::tick() должен вызываться равномерно, автоисточник таймера в этом заголовке предусмотрен только для STM32. Для ESP32 не предполагать аппаратный PWM.
- Flprog_HardwareTimer/src/flprogSystemHardwareTimer.h выбирает реализацию по RT_HW_CORE_ESP32; нельзя предполагать, что 2 импортированных блока получают 2 физически независимых таймера.
- Flprog_Modbus/src/rtu/flprogModbusMasterRTU.h содержит конкретный ModbusMasterRTU с конструктором, принимающим FlprogAbstractUartExecutor*; абстрактные классы и nullptr — не рабочий канал связи.
- RT_HW_200_SoftWire/library.properties объявляет depends=AsyncDelay; отдельной верхнеуровневой папки AsyncDelay в этом архиве нет. До сборки проверить наличие этой зависимости в среде.
- RT_HW_21_SENSORS_2025, LittleFS и часть папок RT_HW_* являются примерами, архивами или коллекциями .hpp, а не самодостаточными Arduino-библиотеками стандартной структуры.
- FLProg_Network здесь имеет версию 1.0.0-rc.6a.dev.20-ntp-timezones: не подменять её API иной публичной версией.
- Некоторые каталоги имеют одинаковое поле name в library.properties (например, RT_HW_20_SENSORS и RT_HW_21_SENSORS_2025); возможны неоднозначности разрешения библиотек.
- В архиве есть тесты/моки, файлы для других платформ и примеры: не добавлять их в итоговый скетч как рабочие зависимости.

ОБЯЗАТЕЛЬНЫЙ РАЗДЕЛ В КАЖДОМ ОТВЕТЕ ИИ «БИБЛИОТЕКИ»
Для каждой задачи до выдачи кода отобразить (и учесть эти сведения в полном русскоязычном описании блока):
- Нужны: точный #include и название библиотеки; если ничего кроме Arduino.h не нужно, сказать это прямо;
- Почему: какая часть задачи реализуется библиотекой;
- Зависимости: что требуется дополнительно (включая FLProg_Utilites/RT_HW/сеть/UART/внешние пакеты, если действительно нужно);
- Совместимость: конкретный ESP32/ESP32-S3/ESP32-C3 и ESP32 Core 2.0.17;
- Совместное использование: GPIO, I2C, SPI, UART, таймеры, LEDC, Wi-Fi/BLE, callback, Flash и память;
- Проверка: просмотр исходника / проверка INO2UBI / компиляция FLProg / испытание на плате — отдельно, без фиктивных результатов.

НЕСКОЛЬКО ПРИМЕРОВ ПРАВИЛЬНОГО ВЫБОРА
А) Задержка включения 2 секунды без блокировки: Arduino.h, millis(); дополнительные библиотеки не нужны.
Б) Чтение BME280: проверить Flprog_RT_HW_ChipsWrappers/flprogBME280.h, его реальный API и RT_HW-зависимости, затем назначение I2C и владельца шины.
В) Modbus RTU master: проверить Flprog_Modbus/flprogModbusMasterRTU.h и Flprog_Utilites; нужен реальный UART executor и физический RS-485 интерфейс, не nullptr.
Г) Управление двигателем с контролем аварий: сначала изучить Flprog_IndustrialAutomation/flprogMotorControl.h, а не писать новый непроверенный драйвер.
Д) ШИМ на ESP32: при необходимости аппаратного ШИМ выбирать поддерживаемый LEDC API ESP32 Core 2.0.17; не считать Flprog_HardwarePWM равноценной заменой.
Е) Веб-панель: сначала проверить, какие внешние блоки FLProg владеют Wi-Fi и веб-сервером; самостоятельный стек (FLProg_Network, K_WEBv20 или ESPAsyncWebServer) в .ubi допустим только по отдельному согласованному требованию.
